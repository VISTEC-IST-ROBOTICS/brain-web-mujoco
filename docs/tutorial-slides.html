Part 1

Robot simulation

A physics engine turns a model and some motor commands into motion, one small time step at a time.

Part 1: the minimum physics-simulation vocabulary needed for the rest.

Robot simulation

A simulator is a loop: state in, state out

Statejoint angles, velocities, base pose
→
Controllerdecides motor targets
→
Physics stepgravity, contacts, actuator forces
→
New stateΔt = 2 ms later

Dynamics

Masses and inertias decide how the robot reacts to forces. Wrong masses = a robot that sags or explodes.

Contacts

Collision shapes touching the floor produce the friction that makes walking possible.

Actuators

Motors turn commands into joint torques. Here, mostly position servos.

Everything a simulator does is in this loop. The controller is the only part we write per robot; the physics step is MuJoCo's job. The three cards are the three things that most often go wrong in a newly imported robot.

Robot simulation

MuJoCo in four words

MjModel: what the robot is

Compiled from the XML. Bodies, joints, geoms, masses, actuators. Does not change while running.

MjData: what the robot is doing

qpos, qvel, ctrl, sensordata, time. Changes every step.

mj_step: advance time

Advances MjData by one timestep, reading ctrl for the actuator commands.

Position actuator

A servo: torque = kp·(target − q) − kv·q̇. We write the target into ctrl; MuJoCo computes the torque.

This vocabulary is used everywhere in the repo. Note that ctrl holds targets, not torques, for position actuators. kp and kv are set per actuator in the XML; the converter defaults are kp=10, kv=0.5.

Robot simulation

Physics fast, control slower

The page steps physics at the model's fixed timestep to keep up with real time. The controller runs at its own rate, in simulated time.

  • Physics: every timestep (e.g. 2 ms, 500 Hz)
  • Controller: every 1 / rate (default 50 Hz)
  • Between ticks, ctrl keeps its last value
  • Same behaviour at any frame rate, browser or desktop
// every animation frame
while (simTime < realTime) {
  if (controlTickDue)
    data.ctrl = controller(obs)
  mj_step(model, data)
}
render(data)
This decoupling is why a controller behaves identically whether the browser runs at 30 or 144 fps. When porting a CoppeliaSim script, rate matters: CoppeliaSim's default step is 50 ms, so Red Mirror uses rate = 20.

Part 2

Robot description

Before you can simulate a robot, you write down its parts, how they connect and how they move.

Part 2: robot description formats. The simulator only understands MJCF, so every robot is converted to it.

Robot description

Many formats in, one format out: MJCF

FormatComes fromIn this repo
CoppeliaSim .tttCoppeliaSim scenesexport_urdf.sh → URDF → urdf_to_mjcf.py (MORF, Red Mirror)
URDFROS, CAD exporters, vendorsurdf_to_mjcf.py, or b1_to_mjcf.py (Unitree B1)
USDNVIDIA Isaac Simusd_to_mjcf.py (Gecko)
MJCFMuJoCo, MuJoCo MenagerieCopy it in directly

All describe the same things: a tree of rigid links joined by joints, each link with mass, shapes to draw and shapes to collide. MJCF also describes actuators, sensors and the world.

URDF is the most common exchange format but has no actuators or floor. MJCF is MuJoCo's native format and includes physics options, actuators and sensors. The converters fill in what URDF lacks.

Robot description

Anatomy of an MJCF file

<mujoco model="hexbot">
  <option integrator="implicitfast"/>
  <asset> meshes, materials </asset>
  <worldbody>
    <geom name="floor" type="plane" size="0 0 0.05"/>
    <body name="robot_base">
      <freejoint/>
      <inertial mass="1.965" diaginertia="…"/>
      <geom type="box" group="3"/>
      <body name="coxa0" pos="…">
        <joint name="TC0" range="-1.57 1.57"/>
        …child bodies: femur, tibia, foot
      </body>
    </body>
  </worldbody>
  <actuator>
    <position name="TC0" joint="TC0" kp="10" kv="0.5"/>
  </actuator>
</mujoco>

body

A rigid link. Nesting = the kinematic tree.

joint

How a body moves relative to its parent. freejoint lets the base fly free.

geom

A shape: drawn, collided, or both.

actuator

A motor on a joint. Its name is what your controller commands.

Simplified from public/assets/morf/morf.xml. The key link to the controller: the actuator names (TC0, CF0, FT0...) are the keys of the dictionary the Python controller returns. Joint names are the keys of obs.qpos.

Robot description

Two kinds of geometry: what you see, what collides

group="1"

Visual geoms

Detailed meshes from CAD. contype="0" conaffinity="0": never collide. density="0": add no mass.

group="3"

Collision geoms

Simple boxes, capsules, spheres. Fast and stable contacts. The web page hides group 3 when a model has visual geoms.

material="printed"

Body colour

Shell parts sharing the printed material get the page's Body colour picker.

Rule of thumb: pretty meshes to look at, primitives to touch the floor. Heavy robots (like the B1) walk much better on primitive collision shapes.

This split is the most common clean-up step. MuJoCo's desktop viewer still shows group 3; press 3 to toggle it. The feet must be collision geoms, or the legs sink through the floor (Red Mirror had exactly this problem).

Repo architecture

A static website. Physics in JavaScript, controllers in Python, no server.

Part 3: how the page is built and how JavaScript and Python cooperate.

Repo architecture

The stack: everything runs in the browser

physics

MuJoCo WASM

@mujoco/mujoco, DeepMind's official WebAssembly build, called from JavaScript.

rendering

Three.js

Copies each geom's pose onto a mesh every frame.

controllers

Pyodide

CPython compiled to WebAssembly. Loaded (~10 MB) only when a robot is opened.

tooling

Vite

Dev server and bundler. No UI framework. Push to main deploys to GitHub Pages.

No backend: the site is static files. And the same controller runs on the desktop with native mujoco for debugging.

Because there is no server, the robot runs on the visitor's machine. Deployment is .github/workflows/deploy.yml.

Python never touches MuJoCo in the browser: the mujoco Python package is not loaded there. JS describes the model once (modelLayout in src/robots/python.js), then on every control tick passes typed arrays over and gets a list of controls back. One crossing per control tick, not per physics step, so it is cheap at 50 Hz.

Repo architecture · JS ↔ Python

One control tick, step by step

1

JS sees a tick is due in simulated time and calls Runner.step_js(...) with typed arrays viewing MuJoCo's memory.

2

Python builds an Observation by name: qpos[qposadr] → obs.qpos["TC0"]; free joint → obs.base_pos.

3

Your Controller.step(obs) returns {actuator name: target}. Missing names keep their value; unknown names raise.

4

JS copies the list into data.ctrl; the next mj_step applies it.

Reset (R)

JS resets MjData (to the first keyframe if any) and calls Runner.reset_js → your reset().

Errors

A Python exception shows a red traceback box. Physics keeps running with the last controls.

Code locations: src/simulation.js for stepping, src/robots/python.js for the bridge (step_js call and data.ctrl.set), python/simbot.py for Runner, Observation and Joy.

Why it works

A controller sees only names and floats, never MuJoCo objects.

What it costs

No mj_forward, no contacts or data.xpos. Need more? Add a <sensor>.

Browser limits

Standard library + Pyodide packages (numpy, scipy). No files, network or threads.

This is the design decision that makes the workflow pleasant: debug with print, breakpoints and matplotlib on the desktop, then the identical file runs in the browser.

Step 1

Get an MJCF model

Path A · CoppeliaSim scene (MORF, Red Mirror)

# A2 export the model root to URDF (headless)
tools/coppeliasim/export_urdf.sh HexBot.ttt /hexbot_body
# A3 check joints and axes in the browser viewer
python tools/coppeliasim/urdf_viewer/server.py

Path B · URDF

Same urdf_to_mjcf.py. Resolve package:// and xacro first.

Path C · MJCF

E.g. MuJoCo Menagerie: copy it in, check floor and actuators.

The converter adds

Free joint, a position actuator per joint (kp=10), floor, lights, placeholder masses.

Set COPPELIASIM_ROOT first. The export script flattens nested shapes so CoppeliaSim's exporter picks up every part; the .ttt is not modified. The converter's summary line reports placeholder inertias: any non-zero count means links that need real masses.
2

Step 2

Clean up the model

A converted model loads but rarely behaves. Copy it to public/assets/hexbot/, then check:

  • Masses match the real robot. MORF's scene had 0.82 kg where 0.082 kg was meant.
  • Unused joints deleted with their actuators (Red Mirror's leg-mount slides).
  • Feet collide: remove contype="0" conaffinity="0" from foot geoms.
  • Collision shapes in group="3" so the page shows meshes, not boxes.
  • Actuator strength: raise kp for heavy robots, cap with forcerange.
  • Body colour (optional): shared material="printed".
  • Model name: <mujoco model="hexbot">.
  • Smaller meshes: tools/stl_to_msh.py. Aim under ~5 MB.
python -c "import mujoco; m = mujoco.MjModel.from_xml_path('public/assets/hexbot/hexbot.xml'); print(m.body_mass.sum())"
Every item here is something MORF or Red Mirror actually needed. Wrong masses are the number one cause of explosions. .msh files are about a third the size of STL with the same geometry; keep the STLs in assets_src to reconvert.
3

Step 3

Check that it stands

$ cp python/robots/_template.py python/robots/hexbot.py
MODEL = "assets/hexbot/hexbot.xml"  # relative to public/
HIDDEN = True                       # out of the menu for now

class Controller:
    rate = 50
    def step(self, obs):
        return {}   # no commands: hold every joint at 0
$ python python/run_local.py hexbot

Expect

Drops onto the floor and stands (or folds up) without jitter, drift or flying away.

If it explodes

Nan, Inf or huge value in QACC: check masses and inertias, then kp/kv on light links, then timestep="0.001".

Then list the names

Print m.actuator(i).name and m.joint(i).name: your controller's vocabulary.

The do-nothing template is the fastest sanity check of a model. HIDDEN = True keeps it out of the menu, but ?robot=hexbot still opens it in the page.
4

Step 4

Write the controller

import math

MODEL = "assets/hexbot/hexbot.xml"
USER_CONTROL = True              # keyboard / gamepad / touch
WATCH_INPUT = {"left_y": 1.0}    # Watch mode walks forward
STAND = {"CF0": -0.5, "FT0": 1.7}  # one entry per actuator

class Controller:
    rate = 50  # control ticks per simulated second

    def reset(self):   # at start and on R
        self.phase = 0.0

    def step(self, obs):
        self.phase += 2*math.pi / self.rate * obs.joy.left_y * obs.speed
        targets = dict(STAND)
        targets["TC0"] = 0.3 * math.sin(self.phase)
        return targets

In

obs: joystick, joint positions and velocities, sensors, base pose.

Out

{actuator name: target}. Left-out actuators keep their value.

Fail early

In __init__(self, robot), check your names against robot.actuators.

A minimal standing pose plus a single oscillating joint driven by the forward stick. Real examples: python/robots/morf.py (tripod gait), red_mirror.py (ported Lua), gecko.py (CPG with visuals, toggle key and touch button).

Step 4 · Controller API

What obs gives you

FieldMeaning
obs.joy.left_yforward / back: W/S, Up/Down, gamepad left stick (−1..1)
obs.joy.right_x, right_ysteer: A/D, Left/Right · up/down: Q/E
obs.joy.keys, toggledheld keys ("Space", "KeyJ") · toggle keys switched on
obs.qpos, obs.qvel{joint name: position / velocity}
obs.sensors{sensor name: value}, float or tuple
obs.base_pos, base_quat, base_velroot body pose (w, x, y, z) and velocity, if it has a free joint
obs.time, obs.speed, obs.watchingsim seconds · speed multiplier · True in Watch mode

Full reference: python/README.md. Shared helpers go in python/robots/_<name>.py, e.g. _heading.HeadingHold.

In Watch mode the sticks are replaced by WATCH_INPUT, so the controller needs no extra code for it. HeadingHold uses base_quat to keep an open-loop gait walking straight.

Step 4 · Porting

From a CoppeliaSim Lua script to Python

Lua · sysCall_actuation

function sysCall_actuation()
  o2 = math.cos(count)*0.4
  count = count + 0.05
  sim.setJointTargetPosition(
      L1_joints[1], o2-0.8)  -- /TL0
end
→

Python · step(obs)

class Controller:
    rate = 20   # 1 / 0.05 s
    def step(self, obs):
        o2 = math.cos(self.count)*0.4
        self.count += 0.05 * obs.joy.left_y
        return {"TL0": o2 - 0.8}

Handles → names

/TL0 is joint TL0 and actuator TL0.

Match the rate

CoppeliaSim steps at 50 ms → rate = 20.

Make it drivable

Scale phase by left_y, steer with right_x, ramp in.

Red Mirror's port, python/robots/red_mirror.py, is the reference. Check joint directions with the URDF viewer's sliders. Open-loop gaits drift; HeadingHold corrects that. Fade the amplitude in over about a second or the robot stumbles at start.
